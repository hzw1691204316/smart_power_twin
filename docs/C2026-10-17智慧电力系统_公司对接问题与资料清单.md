# 智慧电力数字孪生：公司对接问题与资料清单

对接日期：2026-10-17。目标：确定一个可落地试点，拿到真实资料和数据样例，明确公司配合人员及交付时间。

## 一、今天最希望带回来的五项结果

- [ ] 明确一期主要解决什么问题，谁日常使用，怎样算做成功。
- [ ] 确认试点：朝歌服务区及附近收费站的准确名称、范围、上下行关系。
- [ ] 拿到一份设备台账和一张供配电/计量关系图；暂时拿不到时确定提供人和日期。
- [ ] 拿到一份测点说明及一段历史数据样例，确认实时接口由谁对接。
- [ ] 拿到平面图/照片等建模资料，确定业务、电气、接口三个联系人及下一次联调目标。

**不要只记录“有数据、可以提供”。继续问：哪些字段、什么格式、谁负责导出、什么时候能给。**

## 二、开场可以这样介绍项目

“我们目前已完成地图层级导航，以及账号、站点设备台账、电力监测和三维绑定的软件原型，主要用模拟数据测试。希望先选一个服务区和一个收费站，把真实设备、计量关系、监测数据与三维对象对应起来，形成可演示、可验证的试点。今天想重点确认业务目标和资料、接口的获取方式。”

当前边界：有界面和接口原型，不等于已完成现场接入；现有模型是通用样板，不是朝歌站点的测绘模型。自动告警与大屏汇总还需结合公司的规则、指标口径继续完善。

| 必问2 | “主要给谁用？值班人员、运维、电气负责人还是管理层？现在每天最常查哪些内容？” | 账号角色、页面和操作流程 |

| 必问4 | “有设备清单和供配电单线图/计量图吗？全站总表与各分区电表怎样对应？” | 数据库台账与负荷计算口径 |
| 必问5 | “这些设备的数据目前存在哪里？由哪个现有平台或网关采集？能通过现有平台给接口吗？” | 实际数据接入路线，而非凭空选协议 |

| 必问7 | “能否提供站区总平面图、照片、设备位置图？已有CAD、BIM或三维模型吗？” | 模型形状、比例、设备位置，避免只凭照片猜 |

| 必问9 | “一期做到只读监测和查询是否足够？告警由原平台提供，还是希望新系统计算？怎样验收？” | 工作范围、告警来源和完成标准 |
| 必问10 | “业务、电气、接口分别由谁负责？我们最先能拿到哪一包资料，什么时间可以做首次数据联调？” | 会后能推进的具体事项 |

## 四、希望公司提供的资料

| 资料 | 具体内容 | 建议形式 | 对系统的作用 |
| --- | --- | --- | --- |
| 试点站点清单 | 准确名称、业务编码、类型、所属城市/高速、方向、管理单位、参考坐标及坐标系 | Excel/现有台账 | 确认朝歌两站，避免上下行、收费站入口混淆 |
| 站区总平面图 | 建筑、道路、收费车道、停车场、配电房、光伏、储能、充电区的位置及主要尺寸 | CAD/PDF/清晰图像 | 确定真实空间布局和模型比例 |
| 设备台账 | 编码、类型、位置、厂家、型号、额定参数、投运状态、所属站点/区域 | Excel | 替换数据库模拟设备 |
| 电气单线图/计量拓扑 | 变压器、母线、配电柜、进线总表、分区表、光伏并网点、储能、充电馈线关系 | PDF/CAD；没有图可先画简图 | 避免把总表和分表重复累计 |
| 测点/点位表 | 点号、设备对应关系、名称、单位、类型、采样周期、量程/倍率、状态含义 | Excel/接口说明/寄存器表 | 建立device_point及数据解码规则 |
| 历史数据样例 | 最少先取关键设备连续24小时；方便时取一周，包含白天、夜间及一次异常样例 | CSV/Excel/JSON | 检查曲线、时间、缺失、累计量和实际波动 |
| 实时接口资料 | 系统/网关来源、对接方式、请求/消息样例、字段说明、联调环境和联系人 | 接口文档＋样例数据包 | 决定采集程序如何实现 |
| 告警规则与记录 | 阈值、延时、防抖、级别、确认/恢复/关闭流程；几条真实历史事件 | 规则表/平台截图/导出记录 | 为下一个告警模块定规则 |
| 报表与指标口径 | 当前电量、光伏发电、自用/上网、储能充放电、充电负荷等报表 | 原报表/截图/指标说明 | 确认大屏要展示什么以及怎么算 |
| 既有模型与图纸 | 是否已有BIM、IFC、FBX、GLB等，以及使用范围、版本与对应站点 | 原文件及说明 | 评估复用，减少重新建模 |

资料允许用于哪些场景也应当确认：课题开发、组会展示、论文插图、公司演示是否相同；现场照片哪些可以拍、哪些可以带走，由公司明确。

## 五、收费站和服务区的照片怎么要、怎么拍

照片最好与平面图、设备编码一起提供。**只拍一张正面照片，通常无法确定建筑背面、设备位置及尺度。** 先问是否已有现成照片或获准使用的航拍/正射资料，避免要求对方重复采集。

### 1. 收费站

- [ ] 站区全景：收费广场、雨棚、管理建筑与连接道路的相对位置。
- [ ] 收费雨棚：正面、背面、左右侧面；车道数量、通道宽度、柱网、雨棚高度有无图纸尺寸。
- [ ] 雨棚顶面：平顶结构及现有/规划光伏布局；问是否已有设计图，不自行进入屋顶获取资料。
- [ ] 管理建筑：主要立面、层数、屋顶轮廓、门窗及附属房位置。
- [ ] 光伏支架：具体位置、朝向、倾角、排数、组件规格，以现有设计/施工图为准。
- [ ] 配电房、箱变、配电柜、储能、充电设备：远景说明位置，近景说明外观及编码。
- [ ] 路面标线、收费岛、护栏/围栏、标牌、照明、绿化：记录主要布局即可，先不追求每个小细节。

### 2. 服务区

- [ ] 总体全景及上下行两侧关系，是否为独立站区、是否共同管理。
- [ ] 综合楼、餐饮/便利店、卫生间等主体建筑的主要立面及相对位置。
- [ ] 大车、小车停车区域、进出匝道、车行方向和步行区域。
- [ ] 加油/充电区域、光伏车棚、建筑屋顶光伏的实际位置。
- [ ] 配电房、箱变、储能柜、充电桩、照明和主要电气设备。
- [ ] 围栏/护栏、标识、道路、主要绿化带；用于建立真实场景轮廓。

### 3. 每台重点设备至少关联这些信息

| 内容 | 用途 |
| --- | --- |
| 位置远景 | 能知道设备在哪个区域、相邻哪些建筑 |
| 外观正面/侧面 | 用于模型外形、尺寸比例及方向 |
| 铭牌或台账参数 | 确认厂家型号、额定参数；不靠外观猜容量 |
| 设备编号/标签 | 把照片、台账、测点和三维对象对应起来 |
| 位置标注 | 最好在平面图上圈出位置；尺寸优先采用图纸或已知资料 |

可建议命名为“站点编码_设备编码_正面/侧面/位置”，配一张照片索引表。公司已有命名规范时沿用其规范，避免重新编号造成对不上。

## 六、与电气、接口人员进一步确认

### 设备层面

- 每站有哪些实际设备、数量多少？哪些需要单独点击查看，哪些只做场景背景？
- 设备是否已有统一编码？充电桩以整桩、充电枪还是站级平台汇总为管理单位？
- 光伏数据在逆变器、阵列还是全站层级？储能数据在柜、PCS、BMS还是整个系统层级？
- 同一个设备在台账、网关、平台、图纸中名称/编码是否一致？谁能给出对应表？
- 设备是否支持数据采集，哪些暂时没有测点？不能默认每台模型设备都有实时数据。

### 数据接入层面

- 现有系统能提供HTTP接口、MQTT消息、数据库导出，还是必须读取网关/设备协议？先请公司说明实际方案。
- 如果已有平台可提供数据，能否优先通过现有平台接入，减少现场重复采集工作？
- 数据由谁提供、测试环境在哪里、访问需要经过哪些公司内部流程？能否先拿一个完整样例包？
- 时间戳是设备采样时间还是平台接收时间？使用北京时间还是UTC？设备时钟是否统一？
- 采样间隔是多少、可接受的页面延时是多少？多久无数据算陈旧/离线？
- 单位和倍率是什么？例如功率单位kW/W、电量kWh/Wh；寄存器值是否需要倍率、字节顺序或状态码解释？
- 质量异常、断线、无效值如何表示？是否存在0值、空值或固定异常码？
- 历史保留多久、是否可补采、是否有重复消息或同一时刻修订数据？

如果对方是业务人员、不熟悉这些字段，先确定接口/电气联系人，不要求其现场回答所有技术细节。

### 计量和统计层面：非常重要

可以直接拿图问：

> “这个总表是否已经包含充电桩和管理建筑用电？光伏并网点在什么位置？储能的正负功率分别代表充电还是放电？”

进一步确认：

- “全站负荷”从哪个表取值？和购电功率、净交换功率是否为同一个定义？
- 哪些电表是总表，哪些是分表？避免把已经包含的分项再加一次。
- 光伏发电、自发自用、上网电量分别由哪些测点计算？
- 储能充/放电的符号、充电桩功率的含义是否已约定？
- 累计电量有没有清零、换表、倍率变更或设备重启造成的跳变？
- 统计按自然日、班次还是账单周期？分时电价/费用若属于本期，是否有公司采用的现行配置表及生效日期？

暂时没有明确口径时先展示原始读数和趋势，不承诺一个未经确认的“全站能耗”汇总数。

## 七、告警和运维要问什么

- 公司最关注的3—5类异常是什么？先做高温、设备断流、储能SOC、光伏异常中的哪些，还是其他业务规则？
- 阈值由谁定？是否因设备型号、工况或时段不同？持续多久才触发，恢复是否另有条件？
- 人工确认、异常恢复、工单关闭是不是三件不同的事？当前由谁操作？
- 告警是否要定位到模型中的具体设备？公司是否有历史告警记录供核对？
- 通知方式是否在一期范围，还是先在系统内显示？

以上是问题示例，不预设公司一定采用这些规则，也不把目前模拟阈值作为正式阈值。

## 八、部署与验收也要留下答案

- 日常在办公室电脑、笔记本还是大屏上使用？屏幕分辨率、浏览器、设备性能大致如何？
- 系统运行在公司内网还是有互联网访问？地图、模型、字体是否需要本地离线资源？
- 公司是否已有技术栈、数据库、接口、运维或账号接入要求？是否必须对接现有登录体系？
- 不同管理单位和角色能看哪些站点、设备？哪些人能修改绑定或发布场景？
- 一期需要覆盖几个站、几台设备、多少测点？预计后续扩大到什么规模？
- 验收时能否约定：指定设备的模型点击、最新值、时间、历史曲线与公司原系统核对一致？容许多大时间差由公司确认。

当前代码是本机学习/联调原型，现有账号存储与部署方式不能直接当作公司生产交付方案；生产账号安全、网络和运维要求应按公司要求另行落实。

## 十一、资料不齐时，按什么顺序继续

1. 先确认试点身份和业务目标，固定本期范围。
2. 用公司台账替换虚构设备，建立编码对应关系。
3. 先接一台有真实数据的设备，验证单位、时间、质量及历史，再扩展到全站。
4. 按平面图与照片修正模型，区分已建现状和规划方案。
5. 用公司认可的规则实现告警，最后按计量拓扑做汇总。

如果实时接口暂时不能开放，先争取脱敏台账、历史CSV/JSON和接口字段说明，仍可开展数据适配与离线回放。数据应保留真实来源和时间标记，不把历史回放或模拟值标成实时现场数据。
