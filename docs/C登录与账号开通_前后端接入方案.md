## 1. 是否需要登录和注册

**需要登录；首期采用管理员创建账号，不开放公众自助注册。**

这个系统是收费站、服务区的电力运维和数字孪生系统，不是面向所有公众的内容网站。用户需要看到的站点、设备及告警并不相同，修改场景、确认告警、上传采样等动作也需要权限。

登录回答“你是谁”，动作权限回答“你能做什么”，站点授权回答“你能对哪些站点做”。三者应同时存在，不能登录后默认查看所有站点。

| 功能 | 首期建议 | 理由 |
|---|---|---|
| 登录、当前用户 | 实现 | 区分管理员、运维、查看及采集账号 |
| 管理员开户 | 实现 | 站点和角色先核验再授予 |
| 公众自助注册 | 暂不开放 | 陌生人注册没有可信的站点归属和运维身份 |
| 修改本人密码、管理员重置密码 | 后续补齐 | 正式使用前需要，不能只依赖演示账号 |
| 短信、邮箱验证、验证码 | 按部署需求再评估 | 首期内部测试不必同时引入外部服务 |
| 企业单点登录、MFA | 正式部署时评估 | 有统一企业身份平台时可接入，当前不是已实现能力 |

若以后确实有外部合作单位注册需求，可以增加“申请账号→待审核→管理员批准→分配角色与站点”的流程。注册时不能让申请人自行选择管理员角色或任意站点。

## 2. 登录界面如何融入当前前端

建议增加独立的 `/login` 页面，沿用当前海蓝配色、字体和圆角。页面保持简洁：系统名称、账号、密码、登录按钮、必要的错误提示；内部版本不放“免费注册”入口，可写“账号由管理员开通”。

登录成功后，进入原来的全国概览，再按当前全国→省市→站点三维流程使用。登录功能不要求重做已经确认的地图、左右悬浮面板或三维页面。

全局页头显示当前用户和退出入口。地图页与三维页使用不同布局，建议通过共享 `UserMenu.vue` 分别接入 `AppLayout.vue` 和 `TwinDashboardLayout.vue`，避免出现两个重复页头或挤占地图空间。

首期默认保护全部业务页面。若以后需要公开演示，可另设只读公开地图页，只显示公开边界／位置，不调用受保护电力接口，也不暴露账号、告警确认或采样写入。

## 4. 后端放在哪里

沿用根目录后端方案，不新建backend目录：

```text
app/
├── core/
│   └── security.py              # Argon2密码哈希、JWT签发与校验
├── api/
│   └── dependencies.py          # 取当前用户、要求动作权限、注入数据库会话
└── modules/system/
    ├── router.py                # 登录、当前用户、账号、角色、审计入口
    ├── schemas.py               # 登录、开户、站点范围及状态输入
    ├── service.py               # 校验密码、签发令牌、开户、授权和审计
    ├── repository.py            # 查用户、角色、权限和站点范围
    └── models.py                # 六张已有权限／审计表的ORM映射
```

密码采用适合密码存储的哈希，而不是明文保存或普通MD5／SHA摘要；当前正在编写的实现采用 `pwdlib` 的推荐Argon2哈希，JWT使用PyJWT并固定验证算法、期限、签发方及受众。FastAPI官方文档也给出了pwdlib与PyJWT的实现路径。[FastAPI官方安全教程](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/)

JWT是签名凭证，不能在内容里放密码或数据库连接信息。后端每次请求仍查询用户是否有效，并重查动作权限与站点范围；不会只信任令牌里过期的角色快照。

## 5. 数据库不需要再新增一套登录表

已有19张表中的六张可以承担首期职责：

| 表 | 登录模块中的作用 |
|---|---|
| `sys_user` | 账号、密码哈希、显示名称、状态、所属角色 |
| `sys_role` | 角色身份，如管理员、运维、查看用户 |
| `sys_permission` | 动作码，例如site:read、alarm:ack、telemetry:write |
| `role_permission` | 一个角色可以执行哪些动作 |
| `user_site_scope` | 一个用户被授权访问哪些站点 |
| `audit_log` | 账号开通、授权变更、场景发布、告警处置等操作记录 |

首期每个用户一个角色，与已有SQL一致。站点范围为空表示没有站点权限，不能解释成“全部站点”。账号、角色主键用字符串传给前端，避免大整数精度损失。

如果增加公众申请注册、长效刷新会话、全端退出或密码重置票据，需另行设计相关状态存储与迁移；不能假称现有六表已经覆盖所有这些能力。本轮不会自动修改用户的MySQL。

## 6. 前后端登录怎样连接

```text
用户打开受保护业务页
    → 未登录：跳到/login，记住站内返回地址
    → 前端提交账号和密码给POST /api/v1/auth/login
    → 后端查有效用户、校验密码哈希
    → 成功：返回短期访问令牌、用户和权限信息
    → Pinia在内存保存令牌及用户
    → 前端进入原业务页
    → 后续请求附Authorization: Bearer <accessToken>
    → 后端校验令牌、账号、动作权限、站点范围
    → 只返回授权站点的数据
```

登录请求采用JSON，和本项目的HTTPBearer接口约定一致：

```http
POST /api/v1/auth/login
Content-Type: application/json

{
  "username": "demo_admin",
  "password": "DemoAdmin!2026"
}
```

以上是本机演示账号，不能作为真实部署默认账户。MySQL模式不自动创建该账号。

登录响应沿用 `data`／`meta` 外壳，data内包括：

- `accessToken`：访问令牌，不能当作普通用户资料显示或写入日志。
- `tokenType`：bearer。
- `expiresIn`：有效秒数，当前配置默认30分钟。
- `user`：id、username、displayName、roleId、roleCode、permissions、siteIds及账号状态，不含密码哈希。

前端统一请求层示意如下，属于接入说明，不代表已修改现有前端：

```ts
// token来自当前Pinia会话内存，不在这里硬编码演示令牌。
const response = await fetch('/api/v1/sites', {
  headers: { Authorization: `Bearer ${token}` },
})
```

实际调用需要开发代理或后端地址配置；不能让相对路径误请求Vite静态资源服务。统一请求层还需处理超时、非JSON错误和请求取消，不能把接口失败静默替换为演示值。

## 7. 路由守卫怎样嵌入

默认保护全部业务路由；仅登录页标记 `public: true`，账号管理页另标记所需动作码。进入页面前：

1. 未登录或令牌过期，进入 `/login`。
2. 登录有效但没有页面需要的动作权限，展示明确的无权限提示。
3. 登录成功后返回原站内路径；拒绝外部URL、协议相对地址等不可信redirect，避免被引导到外部站点。
4. 退出时清理auth、站点缓存、目录筛选和已选三维设备，防止下一位用户看到上一个账号的数据。

页面守卫、按钮显隐只是交互控制。直接调用接口仍必须由后端检查权限；不能用“前端没显示按钮”代替服务器授权。

401表示身份无效或过期，前端清会话并回登录。403表示没有动作权限，不应反复跳登录形成死循环。当前后端对不存在／未授权的具体站点统一返回404，避免泄露其他站点是否存在。

## 8. 令牌放哪里、刷新和退出怎么处理

首期本机演示采用短期Bearer令牌，只放Pinia内存；刷新浏览器后重新登录。不要把密码、令牌随手放进localStorage或URL。浏览器脚本可以读取Web Storage，OWASP明确不建议把会话标识存入localStorage。[OWASP HTML5安全指南](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html)

如果正式使用需要“刷新页面保持登录”，下一阶段建议评审同源部署与HttpOnly、Secure、SameSite Cookie，配套CSRF防护、服务端会话／刷新令牌撤销和轮换；不是只把当前token改存Cookie就完成了。

当前短期JWT方案中，前端退出只清理本地令牌，不意味着复制出去的令牌已被服务器撤销；锁定／停用账号会因每次重查状态而立即拒绝新请求。若需要真正的全端退出或密码变更后强制失效，需要增加会话或令牌版本设计。以上增强能力尚未实现。

## 9. 角色与站点范围例子（规划与当前实现）

| 角色 | 动作范围 | 站点范围示例 |
|---|---|---|
| 管理员 | 开户、授权、场景发布、查询和处置 | 被明确授予的所有管理站点 |
| 运维人员 | 查设备／监测／告警，确认与关闭已恢复事件 | 朝歌服务区和收费站 |
| 查看人员 | 只读地图业务、模型、监测和告警 | 只授予朝歌服务区 |
| 采集账号 | 只提交测点采样 | 只授予朝歌服务区，不开放账号管理或告警确认 |

上表包含后续规划；本轮只启用ADMIN和VIEWER两种演示角色及台账/账号五个动作码，没有启用运维处置或采集接口。

角色动作与站点范围相互独立。采集账号不能因为有写入动作就向任何pointId上传；后端要从测点反查设备和所属站点后检查范围。大屏统计也要先按用户站点过滤，不能只把地图点隐藏却返回全部电力总量。

## 10. 管理员开户怎样做

```text
管理员登录
    → 打开账号管理页
    → 填账号、显示名称和初始密码
    → 从角色目录选择角色
    → 从本人可管理范围选择站点
    → POST /api/v1/users
    → 后端校验用户名唯一、角色存在且不能超出操作者权限
    → 密码哈希、账号和站点范围同一事务保存
    → 追加脱敏审计
```

后端不能信任前端下拉框：即使篡改roleId或siteIds，也不得授予管理员自己不具备的动作或站点。审计中可以记录用户ID、动作、目标和站点范围，不记录密码、哈希、登录令牌。

后续补“修改本人密码”和“管理员重置密码”时，应核验原密码或管理员权限，并明确会话失效规则；不要通过读出旧密码“找回”。

## 11. 开发地址、跨域与部署

开发前端通常为127.0.0.1:5173，后端为127.0.0.1:8000。两者协议／主机／端口不同会涉及CORS。可采用两种方式：

- 首期通过Vite把 `/api` 代理到后端8000，页面只访问自己的 `/api/v1/...`。
- 或前端直接调用后端地址，后端仅允许明确的前端Origin，以及Authorization、Content-Type和实际需要的方法。

当前后端已配置CORS以支持认证头及POST／PUT业务，前端开发/预览使用Vite同源代理。`localhost` 和 `127.0.0.1` 是不同Origin，需要分别配置。CORS不是身份认证，即使允许Origin也不能跳过令牌和站点权限。

正式部署推荐通过网关将前端与 `/api` 统一到同一HTTPS域名；数据库连接信息只在后端。JWT签名密钥属于后端本地配置，不能放在Vite的VITE_变量中；前端Cesium Token也不能拿来作为系统登录令牌。

之前WinError 10013是后端端口绑定失败，和浏览器CORS不是同一个问题；不能通过改跨域配置解决重复启动占用8000。
