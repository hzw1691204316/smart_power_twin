## 1. 本轮完成的内容

补齐“区域与高速关联”的前后端维护页面，可新增、编辑本站区域，维护区域父子关系，以及本站高速路线的方向、区域、米制桩号、接入方式和主关联。

入口为 **右上角登录用户名 → 站内区域与高速关联**，地址 `/admin/site-relations`。也可以从“站点与设备台账”选中站点，再点击“维护本站区域 / 高速关联”。

复用既有19张表和asset:manage权限，无需新增表或导入新SQL。本轮没有修改你的实际MySQL数据、账号或密码，也没有改地图几何、颜色、GLB模型或登录会话。

## 3. 区域怎样划分

区域表达站内的空间归属，建议先抓主要层级：

```text
服务区站点
├── 北侧站区（DIRECTION）
│   ├── 综合楼（BUILDING）
│   ├── 停车区（PARKING）
│   ├── 充电区（CHARGING）
│   └── 配电及储能区（POWER_ROOM）
└── 南侧站区（DIRECTION）
    └── 按实际设施继续划分
```

这是示意层级，不会自动生成到数据库。上下行定义、实际建筑和设备位置应以公司资料为准，不根据地图朝向猜测。

| 字段 | 含义 |
| --- | --- |
| code | 本站唯一的区域编码，1—64位字母/数字/下划线/连字符，创建后固定 |
| name | 区域显示名称，最多150字 |
| areaType | 类型编码，大写字母开头，最多32位；可用DIRECTION、BUILDING、PARKING、POWER_ROOM、CHARGING、PV、ESS、OTHER等 |
| parentId | 本站父区域数据库ID；顶层为null |

父区域不能跨站、指向自身或形成循环。前端先排除自己与后代选项，后端仍独立检查完整父链。区域改名或调整父关系不自动改变设备所属区域，也不改变模型的物理位置。

区域目前没有独立停用字段，也不提供删除或级联搬移设备。重新归属设备应在设备台账中明确修改areaId。

## 4. 高速关联怎样理解

公共路线与本站关联是两层身份：例如G4是公共路线；“本站G4上行接入”和“本站G4下行接入”是两条独立关联。它们可指向同一路线，但使用不同linkCode和不同方向/桩号/区域。

| 字段 | 含义 |
| --- | --- |
| linkCode | 本站唯一关联编码，如G4_UP，创建后固定 |
| routeId | 已有公共路线数据库ID，不是G4字符串，也不是关联记录ID |
| areaId | 对应本站方向/空间区域，可空 |
| directionCode | UP上行、DOWN下行、BOTH双向、UNKNOWN待核验 |
| directionLabel | 如“往郑州方向”，最多100字，未知留空 |
| chainageM | 桩号对应米数，非负、最多9位整数和3位小数；未知null，0有效 |
| accessType | DIRECT直接接入、INTERCHANGE互通接入、OTHER其他 |
| isPrimary | 本站主关联标记；整个站点最多一个，可全部取消 |

例如 `K23+456.5` 应填 **23456.5米**，不要直接把K字符串填入数值框，也不要填23.4565当米数。

新建/改关联路线只能选择有效路线。原有关联指向停用路线时，可保留并修正原资料，但不能新增该停用路线关联或把它新晋升为主关联。停用站点不允许新增区域/关联，但允许修正既有记录。

设置主关联只切换主标记，不删除其他方向、区域或桩号。历史SQL若已产生多个主标记，保存非主记录可能返回409；应明确选定一条主关联设为true，服务端会原子清除其余主标记。

本页不维护公共路线字典，不上传或修改GeoJSON，也不会改变省市地图上的道路形状。目录缺少某条路线时，应先核验公共路线资料，后续通过资料导入或字典维护补齐，不在本站权限下擅自修改全局数据。

## 5. 修正的衔接问题

- 原普通站点编辑只传primaryRouteId。同一路线有上下行多条关联时，旧逻辑可能把主标记切到首条。本轮优先保留该路线当前主关联，避免保存其他资料时改变方向。
- SiteOut.routes补齐siteId/linkCode/areaId/chainageM/accessType，前端编辑能准确保留原关系资料，不把关联ID和公共路线ID混用。
- 重读目录保留当前仍获授权的站点，不无故跳回首站。
- 保存成功才清编辑器和刷新地图台账缓存；返回台账页会重新读取区域选项。
- 保存成功但后续重读失败时明确提示“保存已成功”，避免重复新增。
- 切站/换账号/撤权/组件卸载使旧响应失效；读取失败不把另一站区域带入当前选择。

本轮没有跨页面实时推送。其他标签页中已打开的设备表单、地图或场景配置应重新进入或刷新，才能读取新的区域/路线资料。

## 6. 接口与权限

所有接口前缀 `/api/v1`，字段camelCase，所有数据库ID用十进制字符串。

| 接口 | 用途 |
| --- | --- |
| POST /sites/{site_id}/areas | 新增本站区域，201 |
| PUT /sites/{site_id}/areas/{area_id} | 完整保存区域名称、类型和父关系 |
| POST /sites/{site_id}/routes | 新增本站路线方向关联，201 |
| PUT /sites/{site_id}/routes/{link_id} | 完整保存关联资料；link_id为关联记录ID |

区域目录沿用GET /sites/{site_id}/areas，关系目录从GET /sites/{site_id}的routes取得，公共路线目录沿用GET /highways。

读取需要site:read。四个写接口需要site:read、asset:manage和本站范围，同时检查后端MySQL写开关。区域/关联不存在或不属于本站统一404；循环、重复编码、停用路线等业务冲突409；非法枚举、精度或额外字段422。

已有C09资产维护权限可复用，本轮没有新权限SQL。原管理员缺asset:manage时核对已有C09脚本，按需要手动授权后重新登录；观察员仍只读。

数据库连接账号与网页登录角色是两层权限。受限连接账号需SELECT已有业务表、site行锁所需UPDATE(id)，site_area与site_route_link的INSERT/UPDATE，以及audit_log的INSERT；本功能不需要DELETE或修改公共highway_route的权限。程序不会自行GRANT。

## 7. 保存、并发与边界

每次维护只保存一条记录。所有本站写操作先锁站点，再用锁定当前读核对区域/关联；MySQL默认可重复读下也不能依赖旧快照检查父环。多个主关联请求可串行成功，最终仍至多一个主关联。

业务写入和操作审计在同一事务中。审计失败时，区域创建、关联创建及此前清除的主标记都会回滚，不留下半次操作。区域/设备/模型关系继续按ID保持。

当前没有多人编辑版本号或自动合并；并发编辑同一记录时后保存者生效。表单编辑期间禁用切站/重读，先保存或取消；离开页面会丢弃未保存输入。前端不保证撤销已经发到后端的写请求。

## 10. 剩余工作与先后顺序

六个基础模块已有首版；本轮区域/关系维护完成后，下一步建议：

1. **资料批量导入**：站点、区域、设备、测点，先预检和错误报告，核对来源与身份后按事务入库；公共路线资料也需核验。
2. **公司真实采集对接**：拿到接口/协议、设备编码、测点表、单位、时间及频率后适配，继续复用现有采样入口，不能用模拟读数冒充现场接入。
3. **能源计量分析**：先明确并网、光伏、储能、充电的计量边界，再做日/月电量、跨站历史趋势、自给率等。
4. **告警完善**：现有数值阈值之外的离线/质量规则、通知与运行任务机制。
5. **部署与运维**：迁移流程、备份恢复、运行日志、部署配置与验收。
6. **三维现场核验**：按公司照片/图纸完善外观、位置和小/大型收费站等尚未制作资源。

本轮到关系维护及验证为止，没有继续扩展上述新模块。
